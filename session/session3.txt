❯ Give me a flow of how a query pair is tested for equivalence

  Searched for 1 pattern, listed 1 directory, ran 2 shell commands (ctrl+o to expand)

⏺ Equivalence is decided without running anything. Each query is parsed and
  rewritten into a canonical string, and the two strings are compared. The
  verdict comes from the first stage that can decide it.

  The flow

  pairs.jsonl line ──► cli.score_pair ──► equivalence.compare ──► Verdict(match,
  score, reason)

  0. Load and dispatch: cli.py (sqleval/cli.py)

  - load_schemas reads every <schema_id>.sql DDL file into a dict.
  - _read_pairs reads the JSONL and skips malformed lines.
  - score_pair (sqleval/cli.py#L28) checks that predicted and ground_truth are
    non-empty. If not, it returns no_prediction or no_ground_truth. It then
    calls compare(gt, pred, schema_ddl), and any exception becomes error:<Type>,
    so one bad pair can't stop the run.
  - With 400 or more pairs and more than one CPU, pairs are scored in a
    multiprocessing pool.

  1. Syntax gate on the prediction: validate.py (sqleval/validate.py)

  - parse_tree(predicted) runs PostgreSQL's real parser (libpg_query through
    pglast).
  - It fails with invalid:* (score 0) if the text is empty, has a syntax error,
    has more than one statement, or isn't a SELECT. SELECT includes VALUES, WITH
    and set operations.
  - _normalize removes location fields and rewrites NOT (x IS NULL) as x IS NOT
    NULL.

  2. Ground-truth analysis, cached: _analyze_gt (sqleval/equivalence.py#L29)

  - Thanks to lru_cache, the same ground truth is analysed only once, however
    many predictions it is compared with.
  - It produces three things: the pg parse tree, the canonical string, and
    whether the query has an outer ORDER BY.
  - If the ground truth won't parse, the verdict is ground_truth_unparseable.

  3. Fast path: identical parse trees

  - If pred_ast == gt_ast, the verdict is identical_parse_tree (match). This
    covers differences in whitespace, keyword case and the case of unquoted
    identifiers.

  4. Parse and resolve with sqlglot: parse_and_qualify
  (sqleval/canonical.py#L278)

  - The Context comes from the schema DDL, built by schema.py
    (sqleval/schema.py). It holds tables, column types, NOT NULL flags, PKs,
    UNIQUE constraints, FKs and enum labels, and it is cached per schema.
  - sqlglot parses the query as Postgres, normalizes identifiers, checks that
    the tables exist and runs qualify, so every column is bound to its table
    alias. It then checks GROUP BY validity.
  - If a column can't be resolved:
    - When Postgres also sees no such column, the verdict is
      invalid:unresolved_column.
    - When Postgres does see the columns, sqlglot has mis-parsed the query, and
      the verdict is Unsupported.
  - Unsupported (from either query) gives no match, with partial credit for text
    similarity (see step 7).

  5. Canonicalize: canonicalize_tree (sqleval/canonical.py#L3315)

  Both queries go through the same rewrite pipeline. The ground truth's
  outer-ORDER-BY flag is passed for both, so ordering only counts when the
  ground truth asks for it. Roughly in order:

  1. Structural cleanup. Strip parentheses, normalize grouping sets and clauses,
     drop LIMIT/OFFSET that do nothing, remove ORDER BYs that can't matter,
     inline deterministic CTEs.
  2. Set operations. Turn UNION into UNION ALL when the rows provably can't
     overlap. Turn recursive tree-walk CTEs and grand-total UNIONs into grouping
     sets.
  3. Alias hygiene. Make aliases unique, resolve ORDER BY aliases, prune unused
     columns of derived tables.
  4. Global rewrites (schema-aware through Resolver). EXCEPT on a key becomes
     NOT EXISTS. Grouped derived tables are merged. ROW_NUMBER() = 1 becomes
     DISTINCT ON. Value sets become semi-joins.
  5. Expression normalization (_norm_expr). Remove double negation, flip NOT
     over comparisons, expand BETWEEN into >= AND <=, turn single-item IN into
     =, turn = ANY into IN, shift typed literal bounds, and so on.
  6. Per-scope rewrites, two passes. These run innermost SELECT first
     (_scope_rewrites (sqleval/canonical.py#L1529)) and use keys and FKs from
     the catalog:
     - RIGHT JOIN becomes LEFT JOIN.
     - Scalar subqueries become joins, and correlated aggregates are
       decorrelated.
     - IN becomes EXISTS, and a LEFT JOIN anti-join becomes NOT EXISTS.
     - Redundant FK joins and self-joins on a key are removed.
     - DISTINCT, GROUP BY columns and NOT NULL checks are dropped when they are
       redundant, and COUNT(col) becomes COUNT(*) when the column is non-null.
     - Equality equivalence classes are computed.
  7. Final pass. Canonicalize counts, convert aggregates to scalar subqueries,
     clean up EXISTS, strip orders again.

  6. Serialize: serialize (sqleval/canonical.py#L3280)

  - The tree becomes a string in which order doesn't matter wherever SQL
    semantics don't care about it:
    - AND/OR terms, FROM relations and GROUP BY keys are sorted sets.
    - The operands of =, <>, + and * are sorted.
    - Equalities are grouped into EQC{...} classes.
  - Aliases are renamed to T:<table>#i. For self-joins, every alias permutation
    is tried (up to 720) and the lexicographically smallest string wins, so the
    choice of alias names doesn't matter.

  7. Decide and score: equivalence.py (sqleval/equivalence.py#L48)

  ┌──────────────────────────────────────────┬───────┬──────────────────────┐
  │                 Outcome                  │ match │        score         │
  ├──────────────────────────────────────────┼───────┼──────────────────────┤
  │ identical_parse_tree / canonical_match   │ ✅    │ 1.0                  │
  ├──────────────────────────────────────────┼───────┼──────────────────────┤
  │                                          │       │ 0.95 × Jaccard of    │
  │ not_equivalent                           │ ❌    │ tokens in the        │
  │                                          │       │ canonical strings    │
  ├──────────────────────────────────────────┼───────┼──────────────────────┤
  │                                          │       │ 0.5 × Jaccard of     │
  │ unsupported / ground_truth_unsupported   │ ❌    │ tokens in the raw    │
  │                                          │       │ SQL                  │
  ├──────────────────────────────────────────┼───────┼──────────────────────┤
  │ invalid:*, ground_truth_unparseable,     │ ❌    │ 0.0                  │
  │ no_prediction, no_ground_truth, error:*  │       │                      │
  └──────────────────────────────────────────┴───────┴──────────────────────┘

  8. Report: _report (sqleval/cli.py#L106)

  - {id, match, score} is written per pair.
  - It prints counts per verdict reason and the match rate per schema.
  - If pairs carry an equivalent label, it also prints a confusion matrix,
    precision, recall and F1, with accuracy broken down by source and category.

  Things to keep in mind

  - A match is only a proof one way. A canonical match means the rewrites showed
    the queries are equivalent. A not_equivalent verdict only means the
    rewrites couldn't line them up; the queries may still be equivalent (a false
    negative).
  - Without a schema, fewer rewrites fire. An unknown schema_id means none of
    the key, FK or NOT NULL rewrites can run, so queries that are equivalent are
    more likely to be scored as non-matches.

⏺ All three come out of build_pairs.py (generator/build_pairs.py). For each of
  the 181 target queries in queries.jsonl (dataset/queries.jsonl), it emits hand

  At a glance

  (generator/pairs/library.py)
  auto (1,230): Rule-based rewrites of the ground truth, in mutations.py

  ────────────────────────────────────────

  auto (1,230): 721 equivalent, 509 not
  malformed (181): All 181 not equivalent
  ────────────────────────────────────────
  Where the label comes from
  hand (635): The author's judgment, plus a note giving the reason
  auto (1,230): The rewrite rule: each rule is either known to preserve meaning
  or known to break it
  malformed (181): By definition: none of these is exactly one valid SELECT
  ────────────────────────────────────────
  category
  hand (635): semantic, or invalid_sql (14 pairs)
  auto (1,230): The name of the rewrite rule (rename_aliases, flip_comparison,
  …)
  malformed (181): The kind of garbage (prose, null, …)
  ────────────────────────────────────────
  Per query
  hand (635): 0–N, as many as the author wrote
  auto (1,230): Up to 4 equivalent and up to 4 not
  malformed (181): Exactly 1
  ────────────────────────────────────────
  What it tests
  hand (635): Real equivalence reasoning
  auto (1,230): The basics: form doesn't matter, any change in meaning is caught
  malformed (181): The syntax gate

  Hand: the hard cases

  These are tuples of (E|N, sql, note), written to look like plausible model
  output. They differ from the ground truth in ways that need real
  understanding:
  - Equivalent, but structured differently. A correlated COUNT(*) > 1 instead of
    GROUP BY … HAVING. IN with DISTINCT instead of a join. '2024-06-01'::date
    instead of DATE '…'. Lowercased camelCase identifiers, which Postgres folds
    to the same names.
  - Not equivalent, with subtle bugs. Grouping by title merges books that share
    a title. Dropping DISTINCT lists two authors with the same name twice. <=
    instead of < on a date. LIMIT with no ORDER BY. 'ON' vs 'on'. Picking the
    wrong table's name column.
  - INVALID: notes. For example, a quoted "bookAuthors", which is
    case-sensitive, so it doesn't match the table bookauthors.

  When the dataset is built, it checks that:
  - every equivalent hand prediction parses and resolves against the schema;
  - a non-equivalent one is also valid, unless its note starts with INVALID:, in
    which case it must fail;
  - no non-equivalent prediction has the same parse tree as the target.

  Auto: wide but shallow

  Every rewrite is applied to the ground truth itself, so it is only ever one
  edit away from it.
  - Equivalent rewrites come in two kinds:
    - Cosmetic (trailing_semicolon, leading_comment, lowercase, reformatting,
      <>/!=). These are checked to leave the Postgres parse tree unchanged, and
      at most one is used per query.
    - Structural (rename_aliases, swap_conjuncts_and_join_sides, implicit_joins,
      count_one, add_order_by_unordered_target). These are sound by
      construction.
  - Breaking rewrites also come in two kinds:
    - Semantic (flip_comparison, change_literal, drop_filter, swap_aggregate,
      left_to_inner_join, flip_null_check, drop_distinct, ordering and limit
      changes, …).
    - Structural, at most one per query (swap_columns, drop_column, plus
      quote_identifiers and unquote_identifiers, which are expected to produce
      invalid SQL).
    - The rules only apply where the change can't accidentally keep the meaning.
      For example, comparisons are only flipped against literals. A breaking
      rewrite must change the parse tree, and except for the quoting ones it
      must still be valid SQL.
  - Which rules get used is random, but seeded from each query's id, so
    rebuilding gives the same pairs.

  Malformed: never a match

  For each query, the builder takes one kind from a fixed list, moving one step
  along the list per query: null, empty, markdown_fenced, two_statements, prose,
  truncated, mysql_backticks, dml_statement (DELETE FROM …), misspelled_keyword
  (SELEC). These test the pglast gate and the no_prediction path in the
  evaluator. They never reach canonicalization.

  How the evaluator does on each

  I ran ./score on the current dataset:

  hand        631/635   99.4%    ← all 4 misses are equivalent pairs scored as
  non-matches (false negatives)
  auto       1230/1230 100.0%
  malformed   181/181  100.0%
  overall: precision 100%, recall 99.6%, 0 false positives

  Hand is the only set that really stresses the evaluator, and it is where all
  the errors are. Auto and malformed mostly guard against regressions: they make
  sure surface changes still match, single-edit bugs are caught and garbage is
  rejected.

  The false positives are real evaluator bugs:

❯ Explain the issues with tyring to resolve them

⏺ Every fix here runs into the same constraint. The evaluator only rewrites a
  query when the rewrite gives the same result on every database the schema
  allows, and it applies the same rewrites to both queries. A missed match costs
  one false negative; an unsound rule can quietly create false positives across
  the whole dataset. So the question for each pair is less "can I make it
  match" and more "can I make it match without matching anything that differs".

  Recursive CTEs (p00227, p00231, p01059)

  - Comparing recursions means comparing fixpoints. Two recursive CTEs are equal
    when their recursions converge to the same set of rows. A normal rewrite
    only changes text, but here you have to show the anchor and the recursive
    step produce the same rows at every round. That needs a small proof engine,
    not a pattern.
  - Cycles change everything. With UNION ALL, a cycle in the data makes the
    query run forever. With UNION, the query stops. p01059 is only equal "if
    there's no cycle". The dataset treats a query that never ends as having no
    result to compare, but encoding that assumption into rewrites is a judgment
    call. Make it too broadly and you start matching UNION with UNION ALL where
    duplicates are real.
  - The outer-query part (p00231) looks easy but isn't local. "Join to the CTE =
    semi-join" needs the CTE's rows to be distinct. For a non-recursive derived
    table, the DISTINCT rules already prove that. For a recursive one you need
    to know UNION is the top operator and that no later step adds duplicates.
    That's provable here, but every variation (a UNION ALL inside, extra
    columns, a depth counter) breaks it. A depth counter is the classic trap:
    UNION no longer removes the same row reached by two different paths, because
    the depths differ.
  - Rewriting the anchor (p00227) is tempting but risky inside recursion.
    Turning a scalar subquery into a join is a normal rewrite. Inside a
    recursive CTE, though, rules that move conditions or tables between the
    anchor and the recursive step can change what each round sees, so I'd have
    to verify every existing rule against recursive scopes.

  WITH TIES (p01984)

  - Easy only in the simplest case. It needs proof that no two output rows tie
    on the full ORDER BY key. Here p.id is the GROUP BY key, so each row has a
    distinct id. But the proof has to run after grouping, joins and DISTINCT, on
    an output that may be NULL-extended. Two rows NULL-extended by an outer
    join can both have a NULL "unique" key and tie.
  - The cost of being wrong is a real false positive. WITH TIES returning 12
    rows instead of 10 is a visible difference. I just fixed that false
    positive, so I'd want the uniqueness proof to reuse the existing "output
    determines the source rows" logic rather than a new check.

  The rounding pairs (p01445, p01522)

  - The problem isn't code, it's the definition of "equivalent". Both pairs
    agree in exact arithmetic and can differ in PostgreSQL's NUMERIC rounding,
    which picks its number of decimal places from the operands' size and scale.
    Matching them means accepting "equal up to rounding".
  - Once you allow that, the boundary is hard to draw. If AVG(x) > k can match
    SUM(x) > k*COUNT(*), why not SUM(a)/n + SUM(b)/n vs SUM(a+b)/n, or reordered
    multiplications? Each looks harmless, but together they make the evaluator
    say "match" for queries that print different digits. That contradicts the
    README's statement that results are compared exactly.
  - The honest option is a separate mode. For example, a "value-tolerant" flag
    that allows rewrites which are exact over the rationals. Then the default
    stays exact and the choice is explicit, rather than buried in a rule.

  LATERAL top-n with grouping (p01914, p01915)

  Three separate pieces are needed, and each is risky on its own:
  1. Pushing a join into a grouped query. In the target, dim_store sits outside
     the lateral subquery; in the prediction, it's inside the GROUP BY. Moving a
     table into a grouped query is only safe when the join can't multiply or
     drop rows inside each group, roughly when you join along a key and every
     row has a match. Get that wrong and every aggregate is silently wrong.
  2. Partitioning by the correlation key. The lateral filters by f.store_key =
     s.store_key and groups inside. The ROW_NUMBER form partitions by
     s.store_key over the joined rows. Proving these produce the same ranking
     means showing the per-store groups are identical sets, which depends on
     step 1.
  3. RANK = ROW_NUMBER (p01915). True only when the partition plus order keys
     can't tie. Here product_key is unique within a store only because it's a
     grouping key. That's the same uniqueness problem as WITH TIES, applied
     inside a window partition.

  The top-n rule I added deliberately stops at a single ungrouped table. Each
  extension multiplies the number of shapes it must reject correctly.

  RANGE INTERVAL window vs correlated subquery (p01297)

  - The two sides sum different things. The window sums per-day totals over a
    7-day frame. The subquery sums raw entries in a date range. They're equal
    because summing daily sums equals summing the entries, which needs SUM to be
    decomposable over the groups and the frame to cover exactly whole groups.
  - Frame semantics are subtle. A RANGE with an interval offset measures by the
    value of the order key, not by row count. It also has edge rules: NULL order
    keys are peers of each other, and the result depends on sort direction. The
    subquery's BETWEEN te.logged_on - 6 AND te.logged_on must match those
    exactly, including that date - 6 is a date, not a timestamp.
  - Only some aggregates work. SUM and COUNT decompose like this; AVG doesn't
    (an average of daily averages isn't the average). So the rule would need
    per-aggregate cases, and a mistake there would be a false positive.

  LEAST / GREATEST pairs (p01944)

  - It's a symmetry argument. The join condition f2.follower = f1.followee AND
    f2.followee = f1.follower is symmetric, so each mutual pair appears in both
    directions, and LEAST/GREATEST maps both to one row. Rewrite rules work on
    structure, not on symmetry, so this doesn't fit the canonicalizer.
  - Very specific, so low value. A rule for it would recognize one idiom
    (normalizing unordered pairs) and is easy to get wrong. For example, if
    follower <> followee is missing, self-follows behave differently on each
    side. Its share of what a model might actually produce is tiny.

  Ratio of table counts (p02080)

  - Several facts must line up:
    - every like references exactly one post (NOT NULL FK);
    - the per-post counts sum to the table count;
    - AVG and ::numeric / are the same PostgreSQL function, down to the digits;
    - both sides are NULL when there are no posts.
  - The FK step is the risky one. It's only valid because the foreign key
    guarantees no "orphan" likes and the column is NOT NULL. If either
    constraint is missing (a nullable FK, or a filter on the posts side), the
    two sides differ. The rule would need to check these at exactly the right
    point.
  - One pattern. Like LEAST/GREATEST, this is a narrow pattern for which "sum of
    grouped counts through a foreign key" is the general rule. Building that
    general rule properly is a decent chunk of work for one pair.

  Cross-cutting costs

  - Rule interactions. Most of these need new rules that fire before or after
    existing ones. In this session alone, ordering mattered several times: a
    second alias pass broke decorrelation, and the window normalization had to
    run once, late. Every new rule adds orderings that can break existing
    matches.
  - Testing burden. Each rule needs a "holds" test and a "near-miss" test, plus
    the stress runs. The near-miss is the hard part: you have to find the
    variation that breaks the rule's assumption, and it's easy to miss one.
    That's how the three holes I fixed last time got in.
  - Speed. Each pass over the tree costs time. Scoring is already about 1.4×
    slower than before; proofs like the recursive-CTE or window-frame ones would
    be heavier still.
  - Diminishing returns. Recall is 99.1% with zero false positives. The
    remaining pairs are mostly one-off idioms. Each would take more code than
    all of group 1 combined, for one or two pairs, and adds risk to a metric
    (precision) that matters more.

  My suggestion: if you want to keep going, do WITH TIES (reuse the existing
  uniqueness proof) and the RANK = ROW_NUMBER part of p01915. Both reuse logic
  that already exists. Decide on the rounding pairs as a definition question (an
  exact vs a tolerant mode) rather than in code, and leave the recursive-CTE,
  window-frame, symmetry and FK-ratio cases as documented misses.
