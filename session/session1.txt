⏺ The repo now matches the layout in the spec. ./score runs end to end on a
  small test file. It doesn't decide equivalence yet: it only counts
  byte-identical queries as a match.

  What's there:
  - score: the executable the spec asks for. It takes --schemas, --pairs and
    --output, writes one line per pair in the required format, prints a summary
    and exits with status 0.
  - sqleval/cli.py: handles the required behaviour around the check itself:
    - A null or empty prediction gets match: false, score: 0.
    - An error on one pair is caught, so it can't abort the whole run.
    - score is set to 1.0 whenever match is true.
    - If the pairs file has equivalent labels, the summary also shows how often
      the verdicts agree with them.
  - sqleval/equivalence.py: holds compare(), which is where the real equivalence
    logic will go. Right now it's a placeholder.
  - dataset/: an empty schemas/ folder plus empty queries.jsonl and pairs.jsonl
    files.
  - generator/: for the programs that build the dataset. tests/ and session/ are
    empty for now.
  - README.md: has the sections the spec requires (schema variation, how scoring
    works, known limitations), each marked TODO.
  - requirements.txt: pins sqlglot==25.34.1, which handles PostgreSQL parsing.
    That's my default choice; we can change it if you'd prefer another parser.
  - .venv/: a Python 3.12 environment with the requirements installed. It's
    listed in .gitignore.

  Your system python3 is version 3.9, so run source .venv/bin/activate before
  calling ./score. Otherwise the script runs under 3.9 and fails on the newer
  type-hint syntax. The graders use 3.12, so this only matters on your machine.

  I haven't committed anything. Next I'd suggest the schemas and the generator,
  then the equivalence logic.

⏺ Saved. Future sessions on this project will know that every schema, target
  query and predicted query is PostgreSQL. That means:

  - Generated DDL and SQL will use Postgres syntax.
  - The harness will parse with dialect="postgres" and won't handle other
    dialects.
  - Equivalence will follow Postgres rules: unquoted names fold to lowercase,
    quoted names keep their case, and integer division truncates (5/2 = 2).

  - Quoting: I varied this on purpose because Postgres treats the two cases very

  joins through junction tables, self-joins, recursive queries over the
  hierarchies, finding rows with no match, window functions, DISTINCT ON, NULL

  / COUNT(*)). Tags come from three places: the SQL's structure, hand-assigned
  labels, and the schema's variation axes.

  What the pairs test. The hand-written pairs focus on cases where comparing the
  SQL text or structure would give the wrong answer:
  - Matches that look different, for example:
    - NOT IN against a column that can't be NULL.
    - A LEFT JOIN that behaves like an INNER JOIN because of a required foreign
      key.
    - <> 'No' on a two-value enum.
    - A redundant IS NOT NULL filter.
  - Near-misses, for example:
    - NOT IN against a nullable ManagerId.
    - COUNT(*) after a LEFT JOIN.
    - Integer division.
    - A filter in WHERE that turns a LEFT JOIN into an inner one.
    - DISTINCT merging different rows that share a name.
    - NULLs sorting first under DESC ... LIMIT.

  How the labels are protected. generator/build_pairs.py refuses to write the
  file if any check fails:
  - Every prediction labeled equivalent must parse with Postgres's parser and
    match the schema, so a typo can't be labeled a match.
  - Hand-written negatives must be valid SQL unless marked INVALID:, and the
    marked ones must actually fail.
  - Purely cosmetic rewrites must leave Postgres's parse tree unchanged.
  - Mutations labeled not equivalent must actually change the query.

  On my first sample of automatic negatives, column swaps and drops made up too
  much of the set. Now each query gets at most one cosmetic positive and at most
  one column-shape or quoting negative. Shorter queries still fall back to
  those when they have few semantic mutations, so they're about a third of the
  automatic negatives.

  Decisions for you to check. I made four judgment calls about what "equivalent"
  means:
  - CHECK constraints are not relied on. The brief defines equivalence using
    column types, primary keys, NOT NULL and foreign keys, and doesn't mention
    CHECK constraints. So no pair is labeled equivalent only because a flag
    column can only hold 0/1.
  - Enum types are relied on. Enums are part of a column's type, so "IsRemote"
    <> 'No' is labeled equivalent to = 'Yes'.
  - Unlinked columns count as independent. For example, quarter = 4 vs month IN
    (10, 11, 12), or IsoCode = 'DE' vs Name = 'Germany'. These are labeled not
    equivalent because no constraint ties the columns together. That's strict,
    but it's what the brief's wording implies. They're a handful of pairs, each
    with a note saying why.
  - Extra fields. Each pair also carries query_id, source, category and note.
    The harness ignores them, but you can strip them if you want the exact five
    fields from the brief.

  How it decides. It only reports a match it can prove. When a rewrite's
  precondition can't be established from the schema, the rewrite is skipped and
  the pair comes back as "no match".
  1. Validity check. The prediction must parse with Postgres's own parser
     (pglast) as exactly one query, and every table and column must exist under
     Postgres's case rules. It's also rejected for an enum value that isn't a
     label of its type, or a selected column that is neither in GROUP BY nor
     covered by a grouped primary key. Postgres raises an error for both.
  2. Fast path. Identical parse trees match immediately.
  3. Canonical form. Both queries are rewritten into a canonical form and
     compared. Each rewrite preserves the result on every database the schema
     allows, for example:
     - NOT IN becomes NOT EXISTS only when neither side can be NULL;
     - a correlated COUNT subquery becomes LEFT JOIN + GROUP BY;
     - a join to a parent table is dropped when only its key is used;
     - GROUP BY and DISTINCT are simplified using primary and unique keys;
     - outer ORDER BY is ignored when the ground truth has none.
  4. Partial credit. Valid non-matches get a 0–0.95 similarity score; invalid
     predictions score 0.

  Soundness checks:
  - Boundary unit tests (tests/test_equivalence.py): each rule is tested on a
    pair where its precondition holds, next to a near-identical pair where it
    doesn't. These tests caught two real false positives, both caused by an
    aggregate inside a subquery being treated as part of the outer query. Both
    are fixed.
  - Stress test: every breaking mutation applied to every target query gave 586
    attempts and no false matches. All 1,448 equivalence-preserving rewrites
    were recognized.

  Known limitations (in the README):
  - The 37 remaining misses are harder equivalences: pre-aggregated subqueries
    vs. a direct GROUP BY, ROW_NUMBER vs. DISTINCT ON, algebraic identities like
    SUM(a - b) = SUM(a) - SUM(b), and date_trunc comparisons.
  - Type errors and runtime errors such as division by zero aren't detected.
  - When sqlglot can't parse something Postgres accepts (e.g. BETWEEN
    SYMMETRIC), the pair is reported as "unsupported" rather than "invalid", and
    only an identical parse tree can match.
